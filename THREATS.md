# TrustVault threat analysis

Scope: a small synthetic-data demonstration, not a production document system. HTTP attackers can change URLs, form fields, verbs and JavaScript; they may hold any public demo account. Application authentication, MySQL and the hosting control plane are separate trust boundaries.

| Threat | Implemented control | Evidence / remaining boundary |
|---|---|---|
| Guess another owner's document ID | SQL restricts list/download to ownership or an explicit grant. No ADMIN content bypass. | `otherOwnerCannotDownloadEvenWithSpoofedParameters`, `administratorHasNoImplicitDocumentAccess`; removing the download condition causes the former to fail. |
| Metadata leaks through listings | Access filtering occurs before records are returned, including names and owner emails. | `ownerListDoesNotExposeOtherOwnersMetadata`, `viewerListStartsEmpty`. Search remains unfinished. |
| Forge ownership in form data | Owner ID comes from the authenticated account; editing has no ownership input. | `ownerCanUploadAndCannotSpoofUploader`, `editGrantAllowsEditingButNeverOwnershipOrPermissionChanges`. |
| Use READ to mutate, or EDIT to delete/re-share | READ only permits reads. EDIT requires current OWNER role and the per-document grant. Delete/share/revoke require actual ownership. | `readGrantCannotEditOrDelete`, `otherOwnerCannotGrantAccessToSomeoneElsesDocument`, `otherOwnerCannotListOrRevokePermissions`. |
| Reuse an old download URL or logged-in session after revocation | Subsequent requests query current grants. Responses use no-store; no signed long-lived file URLs exist. | `revocationBlocksExistingSessionAndOldUrl`, `revokedEditGrantStopsEditing`. Already downloaded copies and a response authorized before revocation cannot be recalled. |
| Race edit/delete against revocation | Mutations lock the document exclusively; grant/revoke hold a shared lock on the same document. Permission checks and writes share a transaction. | Sequential revocation tests pass. Exhaustive concurrent interleaving and load testing are not complete. Deadlocks fail the request and roll back. |
| Reuse a disabled/demoted account's session | Document services check current enabled state/role; the audit service checks current ADMIN status. | `disabledAccountCannotUseItsExistingSession`, `demotedAdministratorCannotUseStaleSessionToReadAudit`. `/api/me` and the legacy admin-check message still reflect session authorities; they expose no other user's documents or audit data. |
| CSRF against upload/edit/delete/sharing | Spring Security CSRF remains enabled. UI fetches the token for mutations. | Missing-token upload/delete tests; real login flow tested. No blanket CSRF exemption. |
| Quietly rewrite/delete audit history through runtime DB account | Runtime grants allow SELECT/INSERT on audit, with no UPDATE, DELETE, DROP or ALTER. No audit mutation API. Audit has no document FK, so deletion preserves history. | `applicationCannotModifyOrRemoveAuditRows`, `ownerDeleteRemovesPermissionsButPreservesHistory`. DBA/hosting administrators are trusted and can alter data; no cryptographic chain or external immutable audit store. A fully compromised application could append false events. |
| Save a change but lose its audit, or release unaudited file bytes | Success audit and business operation commit together; download audits commit before returning bytes. Denials use an independent transaction. | Trigger-injected audit failures test upload, edit, delete, permission grant and download. During a DB outage a denial record may also fail; the request stays blocked and a server error is logged. |
| Reject requests before service code without logging them | Security entry/denial handlers and MVC error handling record anonymous/role/CSRF/invalid-route/invalid-parameter failures. | `anonymousDownloadRejectedAndAudited`, `missingCsrfBlocksUploadAndCreatesAuditRecord`, malformed-route tests. Hosting proxies and Tomcat can reject traffic before application code; those failures require provider/access logs, not the DB trail. |
| SQL injection | User-controlled values use JDBC parameters, not SQL concatenation. | Cross-user tests use spoofed parameters; code review of service queries. Tests do not constitute exhaustive SQL-injection fuzzing. |
| Stored XSS / active file execution | UI uses textContent; filenames and metadata are validated; downloads force attachment and nosniff; CSP restricts scripts to same origin. | Upload validation and download-header tests. PDF marker checks are not antivirus or a full PDF parser; a downloaded malicious file can still harm the user's local viewer. |
| Path traversal / exposed storage | Files are database BLOBs, not static filesystem paths. Simple filenames, Spring's strict firewall and controlled 404s. | `pathTraversalIsRejectedAndAudited`, private configuration route test. |
| Oversized uploads / resource exhaustion | 5 MiB file limit, 6 MiB multipart request limit, bounded reads, latest-100 listing/audit pages, bounded hosted thread/connection pool. | Upload validation review. No total storage quotas or comprehensive request/login rate limits; public users could exhaust resources or brute-force non-demo accounts. |
| Credential interception or repository leakage | BCrypt password hashes, Aiven VERIFY_IDENTITY TLS, hosted secure/HttpOnly/SameSite cookies. Runtime DB password is a private environment value. | Three-account login and cookie/header checks in live script; cloud configuration review. Live TLS and cookies must be verified after actual deployment. Public demo credentials intentionally allow impersonating those demo users. |

An audit DOWNLOAD/SUCCESS means the server authorized and prepared the response after committing its audit record. It does not prove that the client received every byte, opened the file, or read its contents. HEAD requests may record authorization without transmitting the body.

Keep testing and deployment claims separate. `VALIDATION.md` records what was actually run. The live checklist/script must pass on the submitted URL, and the app/database must remain available for judging. A transient tunnel or successful local build is not evidence of reliable hosting.

## Public registration boundary

The role is fixed server-side to OWNER; public registration cannot create ADMIN or inherit document grants. Accounts and their audit record are transactional. Password validation precedes BCrypt hashing; duplicate emails do not replace an account. Registration uses CSRF, no-store responses, parameterized SQL, and bounded process-local signup throttling. Accepted limitations: no email verification (an address is an identifier, not proof of ownership), no distributed throttling, no storage quotas, and duplicate-address responses can reveal account existence. Use synthetic data. Newly registered users cannot review audit metadata; that remains administrator-only.

## Search and deletion follow-up

Search filtering is done in the same parameterized SQL query as the parenthesized document ownership/permission predicate, before LIMIT. LOCATE with parameters treats wildcard and SQL-like text literally. ADMIN does not receive automatic document access. Dates and lengths are validated; date sessions use UTC. The individual metadata route also checks document access and audits both success and refusal.

Do not remove FOR UPDATE to work around a deployment grant failure: it serializes mutation authorization with sharing/revocation. The runtime account needs UPDATE/DELETE only on documents and document_permissions, never on audit_events. An isolated regression test reproduces the missing document privilege, applies the narrow grant, and verifies deletion and retained audit protection. After explicit author approval, the scoped document grant was applied and live owner deletion passed. Audit UPDATE/DELETE remain ungranted.
